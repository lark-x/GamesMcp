2. 如何进一步利用 AnimeGameData 内已有的任务关系、章节、Talk 路径和对白图信息，解决仍然未归区或被拆散的任务？请说明证据优先级、冲突处理和不能自动决定的边界。

4. Wiki 可用于核对大型支线归属和顺序，但正文必须只来自单一源数据。如何把 Wiki 的分类/目录信息安全地转化为可审计的任务映射，而不混入 Wiki 对白？
5. 如何设计候选生成前的一次性审计与门禁，避免逐任务导入、重复跑长流程、反复轮询状态，并保证缺项不会被误标成完整？

本轮希望先得到独立分析和方案对比；不要假设本文中的未完成项已解决，也不要把历史 r13 运行数据说成当前改动已部署。

## 2. 目标与不可违反的约束

- 让原神剧情目录更接近玩家可理解的官方/百科叙事结构：地区 → 大型任务系列 → 子系列或章节 → 具体任务。
- 同一大型支线即使各任务标题差异很大，也应在证据充分时归入同一系列；不能因为标题相似就自动合并。
- 同名但不同 `MainQuest` ID 的任务必须保持独立，不能去重成一条。
- 目录分类和顺序可以参考 Wiki 或人工核验，但**对白正文必须全部来自同一份固定 AnimeGameData 源快照**。Wiki 不得作为对白补丁、缺文填充源或混合语料来源。
- 对源数据没有提供正文、说话人或地区证据的情况，要明确标记缺失/不确定；不能为了表面完整而造正文、猜地区或强行标记 complete。
- 所有人工归类必须基于稳定 ID 或已核验的精确资源路径，带来源、理由和版本；禁止模糊标题相似度匹配。
- 保留已发布旧 revision 和用户数据。未确认连接到真实发布数据库前，不执行迁移、回填、导入或发布。
- 避免对一个个任务重复跑完整转换/导入：规则和映射统一完成、审计通过后，再进行一次完整候选生成。

## 3. 当前已经实现的内容（工作区代码，不等于线上发布）

### 目录模型与规则

- 地区保持目录第一层；大型系列只在一个主要地区出现，任务详情继续保留任务自身的地区。
- 以精确 `MainQuest.chapterId → Chapter.id` 连接章节；章节 `groupId` 不再因为任务不在 `beginQuestId` 锚点列表中而被拒绝。
- 目录投影支持系列、子系列、章节和任务层级，并保留稳定 ID、地区身份和排序信息；没有可靠系列证据的任务可作为地区下独立任务呈现。
- 区分源数据系列、章节组、任务关系、起始任务和人工映射。`requires` 表示前置条件，不单独证明两个任务属于同一系列。
- 系列名不再简单取遍历到的第一条任务标题；章节/任务顺序优先使用可靠章节顺序和方向边，源顺序及 ID 仅作无强证据时的稳定兜底。
- 系列地区采用明确起始章节/任务地区；缺乏起点或出现跨地区证据时不通过多数任务投票猜测。
- 同名不同 ID 仍独立；只在同一目录层级标题冲突时显示 ID 消歧。
- 人工归类通过按 ID 的版本化映射记录，例如 `data/curated/genshin-story-family-overrides.json`。

### 正文解析和 Web/MCP

- 对白归属按 `MainQuest` 主任务 ID，使用明确 `questId` / `mainQuestId`、子任务映射、精确资源路径或节点桥接；不使用相似数字猜测。
- 将叙事对白、控制触发、聚合任务分开，不把 `NpcGroup` 触发信息误作剧情正文。
- 对话节点、边、选项、说话人、分支和语言状态进入正文内容哈希；正文缺失与说话人缺失分别诊断。
- 审计质量状态区分 `complete`、`partial_dialogue`、`speaker_unresolved`、`metadata_only` 和 `source_missing`，附带原因码及 Talk ID。
- 目录对白数量改为根据真实对白关系表/共享正文表，不再采用元数据里的占位数组。
- Web 与 MCP 共用目录投影；类型和关键词筛选对最终目录树生效。页面不再把子任务名称铺成“剧情对白 1…N”的阶段标签。
- 新增按内容哈希共享的只追加正文对象和 revision binding。正文、分页、搜索、引用、实体绑定、MCP 读取支持新旧双读；没有新 binding 的历史版本仍走旧表。
- 增加 r13 分块、事务级、可续跑的幂等 backfill 工具和检查点；默认 dry-run，只有显式 `--apply` 才写入，并校验目标 revision/game/manifest。

## 8. 建议评审输出格式

请按下面结构给出独立意见，尽量引用仓库文件、字段样例和报告中的具体 ID：

1. **结论摘要**：当前根因是否找准；哪些已解决，哪些方案不足。
2. **逐项评审**：地区、系列、章节/任务排序、对白归属、对白图完整性、角色名称、正文质量门禁、性能/回填、页面/MCP 一致性。
3. **更优的核心解析规则**：给出确定性规则的优先级；说明冲突、环、跨地区系列、重复标题、无系列证据和无对白来源的处理。
4. **对 475/158/8/1 的处置方法**：说明应如何批量切分问题类型、从源快照恢复、哪些需要人工/Wiki 目录映射、哪些必须作为源缺失保留。不要假设每项都能自动补齐。
5. **具体建议的数据结构**：至少包含源证据、confidence/quality、映射版本、任务系列/章节关系、未决原因和审计追踪字段。
6. **测试与验收门槛**：给出可执行的单元、集成、全量审计与发布前门禁，避免仅以“程序无异常”判成功。
7. **低耗时执行顺序**：一次源审计 → 汇总分类 → 集中修规则/映射 → 一次候选转换 → 验收/发布；说明长任务如何用事件/单次等待而不是高频轮询。
8. **风险与回滚**：指出对现有 r13、数据库和用户工作区的安全边界。

若建议不同于现有实现，请明确给出能解决的具体失败样例及可能引入的误归类/误合并风险；不要只给原则性建议。
