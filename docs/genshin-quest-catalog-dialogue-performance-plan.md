# GamesMcp 原神剧情目录、对白解析与发布性能重构实施规格

> 本文是供后续开发执行的实施方案。原神对白只使用项目固定的 AnimeGameData 源快照；Wiki 仅用于核对任务归属、章节顺序及人工归类映射，不用于补写对白。

## 一、目标与约束

最终 Web 目录为：

```text
地区
└─ 大型任务系列
   └─ 子系列（仅确有必要时）
      └─ 章节／幕
         └─ 具体任务
```

- 地区仍是第一层。同一大型系列即使任务、章节名称不同，也只在**主要剧情地区**出现一次。任务自己的发生地区另外保存在详情，不因目录归属而被改写。
- 没有可靠大型系列依据的真正独立任务，直接列在地区下，不为每个任务生成一个“任务系列”。无法可靠判断地区时才进入“其他地区”，并记录原因。
- 每个公开剧情任务在目录中恰好出现一次；同名但 ID 不同的任务保持独立。
- 原神正文、角色称呼和对白只来自同一 AnimeGameData 快照。Wiki 仅可用于核对任务归属、章节顺序及人工归类映射，不能补写对白。
- 本轮只处理原神解析和共享读取／存储层；星铁数据不重解析，但必须通过跨游戏回归。当前 r13 及用户文件保留，可回滚。
- 本轮包含数据库内容复用改造。减少状态查询用于节省 token；真正缩短发布耗时依靠减少重复写入。

## 二、核心解析规则

### 1. 先建立任务身份和证据表，再决定目录位置

以 `MainQuest` 的主任务 ID 为唯一身份。对每个任务建立中间记录，至少包含：原始任务类型及公开性、原始标题、子任务 ID、`chapterId`、有效章节行、章节 `groupId`／`cityId`／`beginQuestId`、直接 `seriesId`、经验证的任务关系、Talk 引用、每项证据的来源文件与字段路径。

解析时必须区分：

- **身份依据**：明确的主任务 ID、子任务到主任务的映射。
- **章节依据**：`MainQuest.chapterId → Chapter.id` 的精确连接。章节中的锚点任务列表只作辅助验证，不能当作完整成员名单；当前这一误用遗漏了部分有 `groupId` 的世界任务。
- **系列依据**：章节 `groupId`、有效直接系列 ID、明确的结构性任务关系、经审计的人工映射。
- **顺序依据**：章节编号、可靠的先后任务边、子任务顺序。普通“需要完成某任务”不自动等于“同一故事系列”。
- **地区依据**：有效章节 `cityId`、任务明确的地区来源、经验证的系列继承；文件路径推断只能用于无更强证据且唯一匹配的情况。
- **对白依据**：明确关联到主任务、子任务或 Talk ID 的引用及资源文件。数字接近、标题相似和模糊路径包含均不构成对白归属证据。

中间记录需要保留“原始值、归一化值、采用或拒绝的原因”，使每个最终目录位置都可追溯。

### 2. 地区与大型系列分开计算

每个任务计算 `taskRegionId`，每个大型系列另外计算 `catalogRegionId`：

1. 任务有有效章节且章节 `cityId` 可映射时，使用章节地区。
2. 否则使用任务自身明确、唯一的地区证据；多个互相冲突的地区证据不能任意取第一个。
3. 仍无法确定时，可继承已确认系列的主要地区，但标记为 `inherited`；没有可信系列则进入“其他地区”并列入审计。
4. 已证实源数据地区异常的个案，可用版本化映射覆盖，须写明原始证据和覆盖理由。

系列主要地区优先取**起始章节／起始任务**的明确地区；没有可靠起点时，只有成员地区一致才自动确定。跨地区且起点不明的系列须进入人工映射或阻断发布，不能简单按任务数量投票。目录把全部成员放在这一主要地区，详情仍展示每个任务自己的地区。

### 3. 系列归并的优先级与禁止事项

先形成章节，再形成大型系列；不能在遍历单条任务时临时生成系列名称。归并顺序：

1. **经审计的版本化映射**：用于源数据关系缺失、错误或跨章节标题不一致的已核实案例；明确列出任务或章节 ID，不使用模糊标题规则。映射还可声明“不得合并”的例外。
2. **同一有效章节 `groupId`**：将相应章节置于同一大型系列；组内直接 `seriesId` 可以成为子系列，但不能把大型系列拆开。若一个 `groupId` 混合不兼容任务类型或明显不同地区，先作为冲突处理，不盲目合并。
3. **有效直接系列 ID**：无章节组时使用，但必须检查 ID 对应的名称和成员是否一致；一个 ID 下出现“流放者”“献给某人的蔷薇”这类不同前缀时，不得用遍历到的首个任务标题命名整个系列，应建立经验证的总系列及必要的子系列。
4. **跨章节关系补全**：只有章节标题存在精确、可解析的共同系列前缀，且有可信任务关系或明确章节关联时才自动连接。标题相似本身不够。
5. **结构性关系**：已验证方向的 `starts_after`、`aggregate_of` 可辅助成员归属；`requires` 只证明前置条件，不单独用于系列归并。来源字段语义尚未验证的原始关系只留作诊断。
6. 无以上证据者作为独立任务，不包装成泛称系列。

一个任务若被两套强证据指向不同系列，输出冲突清单并阻止该候选发布；不能静默选择其一。一个系列 ID 在每种语言中必须只有一个稳定展示名，名称由明确源系列名、经验证的章节公共前缀或映射给出。不能用“任务系列”“连续任务”“其他独立任务”冒充真实系列名。

验收样例至少包含：“森林书”四章同一大型系列；“谐律上的咏叙诗”序曲至终章及其关联任务在同一系列；“狮子奋迅”同名不同主任务 ID 不合并；确属同一大系列但名称不同的支线既归在一起，也保留各自章节／子系列标题。

### 4. 顺序不是简单按 ID 或文件行号

- 章节先解析明确的“序章／序曲、第 N 章、第 N 幕、其 N、终章／尾声”等序数；数字和中文数字统一。编号相同或缺失时，才用经验证的剧情关系、`beginQuestId` 和源数据原始顺序。
- 任务顺序在同一章节／系列内按可靠有向关系作稳定拓扑排序；源数据顺序和稳定 ID 只作为无关系节点的兜底。跟踪提示若出现双向边或循环，只能作为弱提示，不能强行决定先后。
- 分支保持偏序关系。循环或矛盾边在审计中列明；显示时对受影响分量作稳定兜底，不能宣称这是有证据的严格剧情顺序。
- 系列在地区中的顺序取其最早、经确认的故事位置，而不是系列 ID 或名称字典序。

### 5. 对白资源与正文完整性的判定

对每个任务先汇总明确的叙事 Talk 引用，再解析来源：

- 接受主／子任务的 `complete_talk`、`TalkExcel.questId`、明确的 `Talk/Quest` 关联、资源内精确 ID、`TalkExcel.initDialog` 与资源内精确对话节点的桥接。NpcGroup 的触发／可用性信息只记录可用性，不当作公开正文。
- 同一 Talk ID 的重复资源按节点 ID、文本及边结构去重。资源内容互补且没有冲突时合并；相同节点出现不同正文或互相矛盾的边时保留歧义诊断，不任意挑一个版本。不能因文件名中的近似数字就认领资源。
- Talk 顺序优先使用子任务和对白图关系，再用源数据明确顺序；不能仅按 Talk ID 数值排列。对话选项、分支及循环结构保留，页面不能把互斥分支伪装成一条线性对话。
- 中文和英文分别从同一快照的对应文本表解析；某语言缺文时标记该语言缺文，不把另一语言文本伪装成完整本地化。角色名缺失时仍保留对白正文，并单独标记角色问题。
- `complete` 要求所有有叙事证据的 Talk 唯一归属、正文可解析且图结构无未解释缺损；`partial` 记录缺失的 Talk／节点／文本；明确无叙事来源的控制或纯元数据任务标记 `metadata_only`。正文数量以实际关系表为准，不读取元数据里的占位数组。

每条非完整记录都要输出：任务 ID、预期 Talk ID、已解析 ID、缺失或歧义资源路径、缺失文本哈希／节点、原因代码及是否属于经证实的上游例外。**有明确正文来源的公开任务不能解析成空正文后仍通过发布。**

## 三、目录模型、MCP 与页面一致性

转换阶段一次性生成包含 `catalogRegionId`、`taskRegionId`、`familyId`、`subseriesId`、`chapterId`、各层稳定顺序、证据来源、`qualityCode` 和 `bodyAvailability` 的目录投影，并将其作为候选版本的一部分持久化。API 和 Web 不在读取时重新推断系列；MCP 返回相同的结构化归属，同时保留旧 `series` 字段作兼容展示。

页面必须：

- 按最终目录树执行类型和关键词筛选；筛选变化后不得被未筛选数据覆盖。
- 对无真实系列名的独立任务直接展示任务；对同名不同 ID 的任务加 ID 区分。
- 展示真实正文完整性状态；去掉无意义的“剧情对白 1～N”阶段标签，默认展示完整任务正文并保留分页。
- 若 API 仍为旧镜像，不能因为新代码或新数据库已完成就报告 Web 验收通过；应核对运行服务的构建标识及数据版本。

## 四、真正减少发布耗时的存储改造

现有发布记录显示一次物化约写入 85 万正文段落、84 万对白节点，耗时约 2 小时 50 分钟；主要瓶颈是每个不可变版本重复落库并维护索引。按以下方式改造：

1. 建立按规范化内容哈希寻址的不可变内容层，容纳文档正文、段落、对白节点及边；哈希输入包含会影响读出的正文、节点、顺序、语言与解析器语义版本，不包含仅影响目录摆放的地区和系列字段。
2. 新版本保存“版本—文档元数据—内容哈希”的归属关系。未变化内容只写新的版本归属，不重插段落／对白和对应全文索引；发生变化的内容才写入新内容层。
3. 适配正文分页、搜索、引用、角色提及、文本绑定和 MCP 读取，使新版本通过归属关系读取共享内容；r13 等旧版本继续使用旧表。迁移期间采用双读取路径，并用同一批任务逐项比较新旧读出结果。
4. 在解析器开发期间预先、一次性地从 r13 建立可复用内容基线。内容层分块、幂等写入并记录检查点；候选仍保持 `preparing`，全部归属和数量校验通过后才原子切换 `current`。失败不影响 r13，不在本轮清理旧内容。
5. 分别测量首次基线建立和之后的“热”候选发布。验收目标是未变段落／对白**不重复插入**，且同等环境下热发布物化时间明显低于现有约 170 分钟基线；具体节省分钟数以实测报告为准，不预先保证。

状态检查另行降噪：运行期间依靠持久化任务状态和低频检查；状态未变化、数据库事务仍正常时不重复读取大报告、不输出例行消息、不重启发布。只在失败、完成或需要人工决策时通知。这样节省 token，但不把它误称为数据库性能优化。

## 五、执行顺序与发布门禁

1. **只读审计**：冻结当前源快照和 r13 基线；输出全量任务的章节连接、系列／地区证据、顺序边、对白覆盖与冲突清单。特别解释当前落入“其他地区”和泛称系列的任务，不为降低数字而强行归类。
2. **规则与单元测试**：完成任务身份、章节连接、地区、系列、顺序、对白及证据模型；用真实边界案例固定预期结果。所有规则统一完成前，不逐个任务重导入。
3. **共享存储与兼容读取**：完成迁移、r13 基线复用、双读取和性能回归；保证旧版本可读、失败可重试、当前版本不受影响。
4. **一次候选构建与导入**：冻结规则及映射后批量转换一次，检查审计差异，再生成下一候选版本。若发现规则缺陷，先修复并重新审计；不得把失败候选当作发布版。
5. **真实服务验收与发布**：逐项核对数据库、MCP、API、Web 的目录及正文；确认容器构建与数据版本一致后发布。保留 r13 作为回滚点。

发布门禁至少包括：

- 所有公开剧情任务恰好一个目录位置；不因跨地区系列重复展示。
- 源数据中能通过 `chapterId` 精确连接的章节成员不再因锚点列表限制而遗漏；系列 ID／名称冲突清零或有明确阻断记录。
- 指定复杂系列分组与章节顺序通过；同名不同 ID 任务不合并，真实独立任务不被塞进伪造系列。
- 有明确对白源的公开任务不为空；未解析和歧义 Talk 全部有逐项原因及证据。确无上游正文的例外可保留，但不能标记“完整”。
- Web 的世界任务筛选仅包含世界任务；当前代码基线约为 1,334 条可读世界任务，任何数量变化须由公开性／归类差异清单解释。此前运行 API 出现过 1,418 条的旧服务结果，必须消除代码与运行镜像不一致。
- 新旧读取在未变内容上的正文、节点、顺序、分页、搜索和引用一致；未变内容不重复物化；旧版本与星铁读取不回归。
